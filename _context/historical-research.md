# Researching a Swift language decision

Start the episode notebook with the question a developer faced at the time. Run one small example using the rules of that release. Identify which result a contemporary reader needed to predict and why the alternative mattered.

1. Follow the proposal file across renames. Read the earliest surviving revision, substantive diffs and final text. Record the commit, status at that revision and what the edit actually changed. Search linked PRs and issues as well as the proposal ID, older title, author and distinctive code. Early records can start after acceptance.
2. Trace the pitch, alternatives, review, returned revisions, decision and later reconsideration wherever records survive. Search Swift Forums and the mailing-list archive. Follow quotations to the speaker. Record dates, roles, concrete examples and reply links. Treat mirrors as a single source.
3. Compare the decision with implementation commits, diagnostic tests, migration guidance and release notes. Distinguish a plan, a compiler change, a warning in a shipped release and final removal. If a phase has no surviving source, record the searches and the remaining gap.
4. In the episode notebook, map each consequential claim to a dated source, speaker or artifact, and what it establishes. Mark inference explicitly. A chronological sequence alone cannot show that a reply changed the outcome.
5. Build the full episode around a documented choice. Let a participant's example explain the cost of one alternative. Show the outcome in code and return to the opening. The Short retains a concrete reason. Before rendering, check each historical scene against the notebook. Display verified public names and handles where available.
6. When later evidence changes a claim, append the correction to the production journal, update the episode notebook and script, and check affected narration, graphics and all four caption tracks. Record reusable research lessons in the wiki and series skill.
